# fix-inject-marker-match

<!--
`free-kiro steering inject` 把 always-mode steering 内容写到错误的 marker
行——把 content 写到 markdown 解释段里的 <!-- free-kiro-managed:start --> /
<!-- free-kiro-managed:end --> 字符串字面量上，而不是真正的独立 marker 行。

根因：`internal/steering/inject.go:201-205` 用 `strings.Contains(line, marker)`
而不是 `strings.TrimSpace(line) == marker`。任何包含 marker 字面量的行
（包括 init 模板里的解释段：`本文件末尾由 <!-- free-kiro-managed:start --> / ...
<!-- free-kiro-managed:end --> marker 包裹的 markdown 块`）都会被误识别
为 marker。

不进 spec 范围：
- 不改 init 模板内容（template 解释段里引用 marker 是设计意图）
- 不改 marker 字符串本身
- 不改 inject 命令的 `--only` / `--dry-run` 行为
- 不动 `assembleBlock` 内部 block 拼接逻辑
-->

## User Stories

- As a free-kiro 使用者 I want `free-kiro steering inject` 只把内容写
  到 markdown 文件末尾的独立 marker 行 so that 解释段里引用 marker 的
  字符串字面量不会被误识别并被覆盖。

- As a free-kiro 维护者 I want `internal/steering/inject_test.go` 新增
  `TestInject_IgnoresMarkerInProse` 反向测试 so that marker 误识别这
  个 bug 不会在 future refactor 中再次出现。

## Acceptance Criteria

[AC-1] WHEN `injectToFile` scans a target file THE SYSTEM SHALL 把
`strings.TrimSpace(line) == InjectMarkerStart` 的行识别为 marker 起点；
任何包含 marker 子串的 prose 行（包括 `本文件末尾由
<!-- free-kiro-managed:start --> /` 解释段）不得被匹配。

[AC-2] WHEN `injectToFile` 已经找到 start marker THE SYSTEM SHALL 同样
用 `strings.TrimSpace(line) == InjectMarkerEnd` 寻找 end marker；start
之前的 prose 行不得被提前匹配为 end。

[AC-3] THE SYSTEM SHALL `internal/steering/inject.go:184-207` 的
`injectToFile` 函数签名 + 行为对外契约保持不变，仍返回 `(bool,
*InjectSkip)`，missing-marker 仍走 `InjectSkip{Reason: "missing inject
marker, run free-kiro init first"}`。

[AC-4] THE SYSTEM SHALL `internal/steering/inject_test.go` 新增
`TestInject_IgnoresMarkerInProse`：构造 prose 段含 marker 字符串字
面量 + 文件末尾独立 marker block 两个区域；调 inject 后断言 prose 段
保持 verbatim + 真 marker block 内填入 product/structure/tech 内容。

[AC-5] THE SYSTEM SHALL `TestStore_InjectAll_WritesBlockIntoMarkerRegion` （已有）与 `TestInject_IgnoresMarkerInProse`（新增）+ 其他 4 个 `Store.Inject` 测试同时 `go test -race ./internal/steering/...` PASS。
[AC-6] IF inject 后 start marker 之前的 prose 行被改写 THEN
`TestInject_IgnoresMarkerInProse` 必须 FAIL；测试用例显式断言
`strings.Contains(proseRegion, "本文件末尾由")` 仍为 true。

[AC-7] THE SYSTEM SHALL 在本仓库根目录跑
`go install ./cmd/free-kiro && free-kiro init --ide claude-code
--overwrite-instructions && free-kiro steering inject` 三步后，
`CLAUDE.md / AGENTS.md / .cursorrules / .cursor/rules/free-kiro.md`
四个文件各自的 marker 行仍在文件末尾（不是解释段），且
`<!-- auto-generated by free-kiro steering inject; do not edit -->`
紧跟 marker start。

[AC-8] WHERE `--dry-run` flag 传入 THE SYSTEM SHALL inject 行为不变：
不写盘，只打印将注入的内容；端到端验证脚本不依赖 `--dry-run`。

## Out of Scope

- 改 init 模板（`internal/ide/templates/instructions_zh.md` 等）里解释段
  引用 marker 字面量的措辞
- 改 marker 常量字符串 `InjectMarkerStart / InjectMarkerEnd` 本身
- 改 `assembleBlock` 内部 block 拼接逻辑
- 改 `free-kiro steering inject` CLI flag（`--dry-run` / `--only`）
- 改 `free-kiro init` 的 CLI 行为
- 改 `internal/steering/store.go` 的 `LoadAll()` / `alwaysDocsSorted()`

## Acceptance Notes

- "独立 marker 行" = 行经 `strings.TrimSpace` 后**完全等于** marker 常量
  字符串。允许前后空白，不允许 inline prose。
- bug 起源：`internal/steering/inject.go:196` `strings.Contains(line,
  InjectMarkerStart)` 是宽松匹配；解释段里
  `本文件末尾由 \`<!-- free-kiro-managed:start -->\` /` 也含子串，被
  误命中。
